# Issue #148 — FACoP → AllasCode prompt/provenance log

This file records the observable implementation trajectory for Issue #148. It deliberately records instructions, implementation decisions and test outcomes, not private chain-of-thought.

## Attempt 0001 — contract import

### Request

Implement `FullAgenticCollab/docs/spec/ALLASCODE-INTEGRATION.md` in `suissa/AllasCode-Blueprint` and make the proposal reusable by AllasCode itself.

### Observed repository state

The commerce example already contained:

- semantic graph compilation;
- semantic change impact;
- selective semantic test execution;
- Action-level unit/load/stress/security/integration/benchmark/synk evidence;
- evidence freshness and provenance;
- semantic merge/release gates.

### Decision

FACoP is implemented as a compiler projection over those existing artifacts, not as a parallel graph or replacement CI model.

## Attempt 0002 — evidence model

Implemented:

- `semantic_id` as canonical Action evidence subject;
- deterministic EvidenceKey over stable Action artifacts + shared semantic/runtime/validation inputs + environment;
- `local`, `dev`, `stage`, `qualification`, `upstream` profiles;
- previous-passport comparison and selective qualification;
- Evidence Passport closure.

## Attempt 0003 — universal validation categories

The existing ActionHarness already executes unit, integration, security, load, stress, benchmark and dependency/synk checks. FACoP adds `chaos` as an explicit category.

If an Action does not declare a meaningful failure-injection surface, its chaos result is `not-applicable` with a mandatory reason. The category never silently disappears.

## Trust boundary

Contributor Action evidence remains under `actions/*/tests/action.test.ts`.

Project-owned stage acceptance remains under the root `tests/`, security audit and E2E acceptance. A contributor therefore cannot redefine the upstream acceptance boundary from inside an Action.

## Expected validation trajectory

1. `issue-148-facop-allascode-integration-dev` → selective contributor evidence.
2. `-stage` adapter branch/PR → upstream unit/integration/E2E/security acceptance.
3. `-tests` adapter branch → target-machine qualification, EvidenceKey reuse/invalidation, public cohort comparison and Evidence Passport.
4. qualified tree → PR to `examples`.

## Attempt 0004 — stage failure proves independent acceptance

The first `dev` run passed. The first upstream `stage` run then failed three commerce integration tests because `run-facop-stage.ts` invoked graph-dependent tests before materializing `generated/semantic-graph.json`.

This was not bypassed. The repair makes semantic graph compilation an explicit upstream stage prerequisite:

```text
semantic-tests:materialize
→ graph:build
→ Action unit
→ project integration
→ project E2E
→ dependency audit
→ security hardening
```

The failure demonstrates the intended FACoP separation: contributor evidence may be green while upstream-controlled acceptance still rejects the candidate.

## Attempt 0005 — qualification separates semantic evidence from runtime outputs

The repaired `dev` and `stage` profiles passed. The first `qualification` then failed after its internal stage acceptance had passed.

Cause: `runtime/test-graph.ts` recursively treated every `result.json` below the project root as semantic test evidence. The stage execution creates operational/runtime artifacts, and one such document did not contain the canonical `artifact`/`test` fields. The graph compiler attempted to read it as a Semantic Test Result and threw before it could produce a validation error.

Repair:

- `.runtime`, `.facop`, `generated`, `node_modules` and `.git` are explicitly excluded from TestGraph discovery;
- semantic result validation happens before graph-node construction;
- malformed candidate documents cannot produce a `TypeError` in the compiler.

This establishes a stronger boundary:

```text
Semantic Evidence Source ≠ Runtime Output ≠ FACoP Output
```

## Attempt 0006 — evidence compiler changes are global semantic inputs

The TestGraph boundary repair initially failed the next `dev` run because `runtime/test-graph.ts` itself was not classified as a global semantic input by `semantic-impact`.

Repair:

- `runtime/test-graph.ts` is now a global semantic input;
- changes to it seed the complete architectural closure;
- the semantic CI policy classifies it as global impact;
- therefore EvidenceKeys and selected validation are invalidated conservatively when the evidence compiler changes.

The resulting invariant is:

```text
Change(Evidence Compiler)
→ Global Semantic Impact
→ Invalidate Dependent Evidence
→ Requalify
```

## Attempt 0007 — typed Semantic Result family

The previous single implicit TestResult contract has been decomposed into an explicit schema family:

```text
schemas/results/
├── semantic-result.schema.yml
├── test-result.schema.yml
├── acceptance-result.schema.yml
├── benchmark-result.schema.yml
├── security-result.schema.yml
├── qualification-result.schema.yml
└── operational-result.schema.yml
```

`semantic-result.schema.yml` is the canonical envelope. Specialized schemas compose it and narrow `semantic_result.kind`. This removes the architectural requirement to infer evidence semantics from the filename `result.json`.

All seven schemas are EvidenceKey inputs.

## Attempt 0008 — CI/CD becomes a compiled 2flow source

CI/CD is no longer semantically defined by hand-written GitHub workflow YAML. The project now binds `config.yml#flows.ci-cd` and `facop.ci-cd` to `./ci-cd.2flow`.

`ci-cd.2flow` defines:

- `FACoP.Dev` — semantic-impact-selected contributor evidence;
- `FACoP.Stage` — project-owned acceptance;
- `FACoP.Tests` — target-server characterization, public cohort comparison, dashboard, security intelligence and qualification;
- every existing commerce Action as a graph node;
- `:--:`, `[...]`, `!->` and `[? ...]` topology;
- `->`, `<-`, `->>` and `<<-` execution wiring for Action evidence and compiler-owned FACoP capabilities.

The invariant is now:

```text
manifest.yml + config.yml + schemas/results/*.yml + ci-cd.2flow + semantic graph
  → AllasCode/FACoP Compiler
  → execution plan
  → GitHub/local/other adapter projection
  → typed Semantic Results
  → Evidence Passport
```

`ci-cd.2flow` and the result schemas are included in every Action EvidenceKey, so changing the semantics of validation invalidates prior evidence rather than silently reusing it.
